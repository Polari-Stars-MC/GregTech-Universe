## 一、核心设计决策：questId 是**派生的**，不是字面量

### 问题

FTB Quests 的 questId 约束未知（8 位？十六进制？只能 `[0-9A-F]`？）。
而 6 章 × 1280 条任务里，如果每条都手写 questId 字面量：
- 约束一旦确定，**1280 条全部要改**
- 手写本身也是错误来源

### 解法

**内容层永远不写 questId。** questId 由 `(章, 模块, 槽位)` 三元组在编译期派生。

```java
/** 任务坐标 —— 内容层唯一需要表达的东西 */
public record QuestCoords(int chapter, int module, int slot) {
    // ⚠️ slot 范围是 1~20，不是 1~16
    //    E-05 删的是槽位 12/17/18/19，但保留 01（场地确认）与 20（桥接成果）作为无检测过渡任务，
    //    所以 slot=20 合法。若写成 >16，末尾过渡任务会直接抛异常。
    public QuestCoords {
        if (chapter < 0 || chapter > 99)   throw new IllegalArgumentException("chapter: " + chapter);
        if (module  < 0 || module  > 19)   throw new IllegalArgumentException("module: " + module);
        if (slot    < 1 || slot    > 20)   throw new IllegalArgumentException("slot: " + slot);
    }
}
```

```java
/** questId 派生器 —— 全局唯一一处格式定义 */
public final class QuestId {
    // ⚠️ 以下参数在 D0-01 核实后调整；调整只改这一个类
    private static final int  PREFIX_LEN = 2;        // 0 / 2 / 3
    private static final char PAD          = '0';
    private static final boolean HEX       = false;  // true → 用 A-F 编码

    public static String of(QuestCoords c) { ... }   // 02,00,01 → 见下表
}
```

### 约束未知时的应对

| 核实结果 | 调整 | 影响面 |
|---|---|---|
| 8 位任意字符 | `PREFIX_LEN = 2` → `GT020001` | **改 1 个类** |
| 8 位纯十六进制 | `HEX = true` | **改 1 个类** |
| 6 位十进制即可 | `PREFIX_LEN = 0` → `020001` | **改 1 个类** |
| 有长度上限 / 字符集校验 | 在 `of()` 里加断言 | **改 1 个类** |

> **1280 条内容零改动。** 这是「让问题不重要」的具体含义。

### 内容层的写法

```java
// ❌ 现在文档里的写法（不可行）
id: "120001"

// ✅ 派生写法
id: QuestId.of(new QuestCoords(2, 0, 1))
```

## 二、命名锚点（F-02）

### 章注册

```java
public final class ChapterEntry {
    // 每章一个稳定锚点，不随裁剪 / 重排改变
    public static ChapterEntry key(String anchor);
}
```

| 章 | 锚点 |
|---|---|
| 00 机械纪元 | `mechanical_era` |
| 01 蒸汽时代 | `steam_age` |
| 02 内燃机纪元 | `combustion_age` |
| 03 LV | `lv` |
| 04 MV | `mv` |
| 05 HV | `hv` |

### 跨章依赖

```java
// ❌ 现在文档里的写法：硬编码数字 ID
// 02-001  前置任务：01-400     ← ch01 裁剪后立即失效

// ✅ 锚点：自动解析到该章「实际末条」
ChapterEntry.prev("steam_age")
```

`prev()` 的解析时机在**任务图装配阶段**，而不是内容编写阶段。
任何一章裁剪、插入、重排，其余章的依赖**自动跟随**。

> **收益量化**：F-04 决定 ch04/05 并行实施，两条轨道会同时改章注册表。
> 锚点机制让它们**改不到同一处** —— 这是并行安全的必要条件，不只是防断链。

### 抽检失效保护（F-03 的配套）

```
若抽检在模块 M 中命中 1 处错误
    → 模块 M 的全部 14 行回退重审
    → 不是只修错的那一行
```

理由：错误往往成簇（选错主设备会连带选错其构件、产物、产能）。
只修单行会导致「同一个错误换 4 个皮」。
